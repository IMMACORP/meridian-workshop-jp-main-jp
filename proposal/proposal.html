1.エグゼクティブサマリー

御社の課題は、ダッシュボードが動かないことではありません。オペレーションチームが、画面に出ている数字を信用できないことです。期間や拠点を切り替えても概要ページの指標が変わらない以上、チームが表計算ソフトで集計をやり直すのは合理的な判断です。同時に、自動テストがないために IT 部門が変更を止めざるを得ず、問題を直そうとするほど承認が通りにくくなる——この膠着が今の本質だと理解しています。

そこで本提案では、最初の3週間で「概要ページの修正」と「その範囲を守る自動テスト」だけを納品します。スコープを意図的に小さく切ったのは、2つの理由からです。第一に、オペレーションチームが最も困っている点を最短で解消するため。第二に、IT 部門に対して、私たちの変更がテストで保証されることを、残りの作業に着手する前に実物で示すためです。信頼を言葉ではなく、動くものと緑のテストで証明してから次に進みます。

本提案は、RFP に同梱いただいたソースコードを実際に読んだうえで作成しました。その結果、引き継ぎ資料の記述と実装が食い違う箇所を複数確認しています（詳細は §2.1）。なかでも重要なのは、国際化対応（D2）が資料に一切記載がないまま、すでに大部分実装されていたことです。この発見により、D2 は当初想定より大幅に低コストで提供できます。希望項目のうち D2（i18n）と D3（ダークモード）を本体スコープに含めてご提案できるのは、この事前調査の結果です。

価格はフェーズごとの固定報酬とし、総額 148,000 USD（14週間） を提示します。各フェーズが独立して価値を持つ構成のため、御社はフェーズの区切りごとに継続可否を判断できます。前任ベンダーが仕事を未完のまま残した経緯を踏まえ、「全部まとめて着手して、全部中途半端」という事態が構造的に起こらない契約形態にしています。

2.2　R1: 概要ページの改修 — 最優先

想定している原因。フィルターの状態は useFilters.js composable が保持し、各ビューがそれを参照する設計になっています。概要ページの指標が反応しない以上、(a) フィルター値が API リクエストに渡っていない、(b) 渡っているがバックエンドで適用されていない、(c) 適用されているがフロント側の算出プロパティが依存関係を取りこぼしてリアクティブに再計算されていない、のいずれかです。Dashboard.vue が 1,271行と大きく、指標ごとに実装経路が異なる可能性があるため、指標を1つずつ潰す方針を取ります。

進め方。

  1. 概要ページの全 KPI を棚卸しし、「どのフィルターに反応すべきか」の期待値表を御社と合意する
  2. 各 KPI について、フィルター適用の経路（Vue → api.js → FastAPI → 集計 → computed）のどこで切れているかを特定する
  3. 修正する。併せて、同じ原因が他ビューにも及んでいないか横展開で確認する
  4. 期待値表をそのまま E2E テストに落とす（§2.5）

期待値表を先に合意するのは、「直った」の定義を御社と私たちで一致させるためです。この表が、そのまま検収条件とテストケースになります。

2.3　R2: Reports モジュールの改修

御社が記録されている8件以上の問題について、まず再現と分類を行います。§2.1 の調査から、少なくとも以下は確定しています。

  • 国際化対応の不備: Reports.vue は i18n 未対応。日本語表示に切り替えても英語のまま（D2 と一体で解消）
  • 実装の逸脱: 唯一 api.js を経由せず axios を直接呼んでいる。フィルター状態の共有機構から外れているため、「フィルターの一部が未接続」の原因である可能性が高い
  • データパターンの不整合: /api/reports/quarterly と /api/reports/monthly-trends を別々に取得しており、集計の整合が取れていない疑いがある

前提条件。御社が記録されている8件のリストをキックオフ時にご提供ください。私たちの調査結果と突き合わせ、着手前に対象を一覧として確定し、固定報酬の範囲を書面で合意します。合意したリストにない問題が後から見つかった場合は、重大度を評価のうえ、本フェーズに含めるか次フェーズに回すかを都度ご相談します（§2.8）。

2.4　R3: 発注推奨機能（Restocking ビュー）

現在の在庫水準（inventory.json）、需要予測（demand_forecasts.json）、およびオペレーターが指定する予算上限から、発注候補を算出して提示するビューを新設します。

設計方針。推奨ロジックは「ブラックボックスにしない」ことを最優先にします。Tanaka 様のチームが推奨をそのまま発注に使えるかどうかは、なぜその数量なのかが画面上で説明できるかにかかっているためです。各推奨行には、算出根拠（現在庫、予測需要、リードタイム、不足見込み）を展開表示します。

前提条件。発注点の算出式（安全在庫の考え方、リードタイムの扱い、予算超過時の優先順位）は、業務ルールとして御社にご決定いただく必要があります。フェーズ3の冒頭に2時間程度のワークショップを設定し、そこで確定させてから実装に入ります。既定の算出式はこちらから叩き台をご用意します。

データ層について。purchase_orders.json が空配列であることから、発注データの永続化は未実装と判断しています。本提案では既存構成に合わせて JSON ファイルへの書き込みで実装しますが、発注履歴が業務データとして蓄積されるものである以上、将来的にはデータベースへの移行をお勧めします（本提案のスコープ外、§2.7）。

2.5　R4: ブラウザテストの自動化 — 全フェーズに分散

R4 は、他のすべてを前に進めるための前提条件だと理解しています。そのため独立したフェーズにはせず、フェーズ1から継続的に積み上げます。最後にまとめて書くテストは、往々にして「今の実装が通ること」を確認するだけのものになり、IT 部門が求めている保証にならないためです。

2.7　本提案のスコープ外とする項目

3.関連実績

事例1: 既存システムへの回帰テスト自動化の段階導入エンタープライズセキュリティ ／ 顧客規模非公開

数百万行のコードを持ち、複数のプラットフォームに対応する既存製品において、頻繁な改修に伴う回帰テストの負担が課題となっていた。FPT ソフトウェアは、手動テストを通じて業務フローを理解したうえで、安定したモジュールから自動化を開始。オンサイト・オフショアの6名体制でテストフレームワークを構築し、再利用可能なテストスクリプトによって保守時の工数・コスト削減を支援した。

本案件との関連: R4 における既存システムへの段階的なテスト導入、および改修に伴う回帰確認の仕組みづくり。

事例2: 実業務シナリオに基づく受入テストの自動化国内小売・卸売 ／ 全国300店舗以上

全国に300店舗以上を展開する日本の小売・卸売企業に対し、FPT ソフトウェアは取引管理システムの受入テスト自動化を提案。RPA を用いて、100名が同時にシステムを利用する実業務の操作を再現し、手動で実施していた検証の自動化を支援した。

本案件との関連: R4 において、実装単位ではなく、現場の利用シナリオを起点にテストと受入確認を設計する考え方。

事例3: 流通管理システム刷新によるデータ活用とレポート業務の改善消費財製造 ／ ベトナム大手

複雑な既存システムを持つ消費財メーカーに対し、FPT ソフトウェアは流通管理システムの刷新を支援。在庫・購買・発注などの業務を統合し、業務プロセスの定義から導入、利用者教育、稼働後支援まで対応した。実データに基づくレポート作成を可能にし、週次報告の作成時間短縮と予測精度の改善を実現した。

本案件との関連: R1・R2 の業務データと表示・集計結果の整合性を重視する方針、および R3 の在庫・購買・発注業務への理解。

事例4: 需要予測と既存在庫システムの連携による在庫管理の高度化国内大手調査・コンサルティング企業 ／ 医薬品領域

製薬企業・薬局向けに在庫・流通・発注システムを提供する日本の大手企業に対し、FPT ソフトウェアは処方量を予測する AI ソリューションを構築。予測結果を RPA で既存在庫システムへ取り込み、在庫管理を自動化した。公開事例では、需要予測精度98％、欠品率4％、売れ残り在庫金額8％削減の成果が報告されている。

本案件との関連: R3 における需要予測データの在庫管理への活用、および既存システムを活かした機能拡張。なお、本案件の発注推奨は、合意した業務ルールに基づく設計を前提とする。

体制。本案件はオンサイトとオフショアを組み合わせた最大6名体制で臨みます。事例1・事例2で用いたのと同じ体制の取り方です。

窓口はオンサイトのプロジェクトマネージャーとリードエンジニアに一本化し、Tanaka 様のチームおよび IT 部門とのやり取りで御社に負担が分散しないようにします。フェーズを通じて同一のメンバーが担当し、途中での交代は行いません。

5.なぜ FPT ソフトウェアか

前任ベンダーの件について、御社の見立ては「能力はあったが、案件を抱え込みすぎて未完のまま残していった」と伺っています。私たちはその再発を、意思や努力ではなく契約の構造で防ぎます。

  • フェーズを小さく切り、各フェーズが単独で価値を持つように設計しました。途中で止まっても、使えるものが残ります
  • テストを最後にまとめず、フェーズ1から積み上げます。IT 部門の承認が後工程のボトルネックになりません
  • スコープ外の項目を §2.7 に明記しました。やらないことを先に書くのは、やると書いたことを確実に納めるためです

そして、本提案に記載した見積もりは、同梱いただいたコードを実際に読んだうえで作成しています。引き継ぎ資料との差分3件（§2.1）は、その過程で見つけたものです。着手してから「思っていたのと違った」と申し上げることのないよう、分かる範囲は先に調べました。
